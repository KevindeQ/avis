# Avis
This project aims to build a virtual 3D environment in which autonomous driving vehicle models can be developed, evaluated and demonstrated.
Eventually, the idea is to build a set of applications which are able to communicate with each other to achieve the project aim. For this design iteration, only development and demonstration of autonomous driving vehicle models is considered. Evaluation of vehicle models is postponed until a later design iteration.

The set of applications to run the autonomous driving vehicle models should be implemented using C++23 with CMake as the meta-build tool. Only Windows 11 needs to be considered as target. Earlier Windows versions should not be supported. Several libraries are available in the folder `external/` to make the implementation simpler.
For the implementation of tools, python should be used as the preferred language. The scope of the python language for the current implementation is its usage to implement tools for things like data management. For example, as a preprocessing tool for packing sensor data in a custom format that is easier to read. It doesn't need to be considered as a scripting language to be used within the Visualizer or driver application.

## Architecture
The overall architecture consists of two applications. The first application will be Visualizer. It provides the functionality to interact with the simulation. In other words, it is supposed to be the application that allows editing of the scenario and controlling the simulation. The second application is driver. This application will be the vehicle model host. It is responsible for handling vehicle dynamics simulation. Communication between the two applications should happen based on the Zenoh library/protocol. Data is send between the two application based on a custom binary message set. The contents of the messages is to be determined at a later design iteration.

The visualizer application owns of the simulation state and the clock. It is the driver of the simulation and should be in charge of the time steps that happen in the simulation. The sensors that should be supported are camera, lidar and GNSS/IMU.

To keep the two applications in sync. A lockstep based execution was chosen where the visualizer application sends pulses to the driver application to know when to advance the vehicle simulation. When lockstep execution fails due to communication errors, the simulation should pause.

Both applications should be robust against errors as the application will be used as development tool. As such, it is to be expected that the vehicle models might produce unintended errors. The Visualizer application should not crash as result of errors in the driver application. As error handling policy, use std::expected when possible. But fallback to exceptions when the error is to severe to continue.

The applications do not necessarily need to run on the machine. It should also be possible to run the applications on a network of connected computers. An example mapping could be that the visualizer runs on a computer with a graphics card, while the driver runs on a server with ample compute power.

## Key components
The following are key components that should be developed in this codebase.

### Application: Visualizer
Visualizer is a native application that will be used to control the development and demonstration of vehicle models. It is the intended owner of the simulation state and the clock. It should be capable of real-time 3D rendering a scene in which entities can move around. The main loop of the application should be based on a virtual clock to ensure the simulation can be deterministic across different runs. The virtual clock should be a fixed timestep clock where the delta time is configurable. The clock should be able to run at the same speed as the wall clock or when told it should be able to run slower or faster than the wall clock. It doesn't need to be concerned with rewinding.

The scene management of the entities should happen based on the scene management capabilities provided in the Avis library.

The 3D rendering should use the 3D rendering framework developed in the Avis library. The scene rendering architecture should be implemented as a combination of a forward rendering pipeline (for transparant materials) and a clustered deferred rendering pipeline. For shadows use cascaded shadow maps. The rendering pipeline should be build upon the render graph from the avis library. The render passes should at least consist of a depth pass, a linearize depth pass, a gbuffer pass, a lighting pass and a ambient occlusion pass. In addition, also include render passes for tone mapping and anti-aliasing. The lighting pass should use a PBR based lighting model. For the ambient occlusion, GTAO should be used. The ambient occlusion should not use an external implementation but implement its own version. For anti-aliasing, use temporal anti-aliasing (TAA). For debugging, it might be handy to have a rendering pass in which it would be possible to inspect the different inputs and/or outputs of the specific rendering passes. The debug rendering pass should be a render pass that blits selected resources.

The frame rendering and simulation tick should operate independently from each other. When rendering happens in between simulation ticks, the scene poses should be interpolated accordingly with the passed simulation time.

If it is not possible for the driver to keep up with the requested speed, the simulation clock should silently slow down to keep deterministic behaviour.

For the user interface, other than the 3D rendering of the scene, the Qt framework version 6.11.1 should be used. The user interface should be based on the usage of Qt Quick and QML. The current iteration of the visualizer application should have a basic user interface with simple menus and the ability to show real-time 3D rendered scenes. Integration of the 3D viewport should be based on QQuickRhiItem. Additional components that should be considered for the application: the application should have a scene tree view that shows all entities that are currently in a scene. Besides this, an entity inspector would be a nice addition to inspect the properties of an entity. This allows users to inspect the state of different entities. It should also have controls for manipulating the camera of the 3D scene. The application should also have controls to be able to start and pause the simulation.

Qt QRHI integration with the RHI implementation within Avis should be done based on separate devices. Textures to be displayed in the user interface should be shared using shared handles and fences.

Simulation should happen based on scenarios. These should be defined in custom YAML files. The YAML files should be be able to be editted by the Visualizer application. Editting of scenarios is only allowed while a simulation is stopped.

### Application: Driver
The driver application is an application to host the vehicle model that are to be developed by users. It should be structured such that it performs a simulation step when it gets an external signal that a timestep has passed. The vehicle model is likely going to be a kinematic model combined with physic simulation based on a physics engine.

In the current design iteration, I would like to use the KITTI-360 as input to the driver vehicle model. The sensor data from the KITTI-360 dataset should be used as the basis for the sensor data on which the driver bases its decisions.

The driver should be responsible for extracting information from the sensor data about other road users such as cars, bikes and / or pedestrians or pets. The scenario configuration should be such that a selection can be made from the KITTI-360 about which data should be used for a scenario.

### Library: Avis
The Avis library should be a collection of generic library components that will be used to implement specific applications within this codebase. In its current iteration, the library should have a generic 3D graphics rendering engine that is able to render 3D scenes in real-time. Use the Eigen library, available in `external/eigen-5.0.1/` as the math library.

The 3D rendering engine should be split in two parts.
The first component is a low-level interface to the render hardware. The name of this component is RHI and this should use the DirectX 12 API to interface with the available graphics card. Only DirectX 12 should be supported as underlying graphics API. Vulkan should not be a concern. However, users of the interface should be agnostic to the underlying graphics API. In other words, DirectX 12 specific structures or classes should not leak from this interface. The low-level interface should be generic and agnostic to specific renderer implementations, such as deferred rendering. HDR output is out of scope for the current design iteration.

It should take care of the following:
- Configurable number of frames in flight.
- D3D device management.
- Command list allocation, recording, execution and execution tracking. Note that command recording should support multi-threaded command recording.
- Utilize async compute and the copy queue besides the graphics queue to get better graphics card utilization.
- Pipeline state object management. The use of pipeline libraries is not necessary.
- Shader management. Shaders should be compiled offline by DXC at build time. DXC should write the compiled shaders to file and these should be loaded when needed. Hot reload of shaders does not need to be considered.
- GPU resource pipeline binding. Pipeline binding should be implemented according to the bindless resource binding technique. For this, make sure the graphics card at least support Shader Model 6.6. If this Shader Model is not supported then the application should not be able to start.
- Use enhanded resource barriers. Do not use the Agility SDK for this feature. Use the APIs available in DirectX 12.
- GPU resource allocation and lifetime management for resources such as textures, buffers and constant buffers.
- Use a staging ring buffer as intermediate buffer to upload resources to GPU memory
- Include support for readback of resources to the CPU
- For debugging purposes, have the ability to configure that the DirectX12 debug layer and GPU-based validation should be enabled.

For the descriptor heap layout maintain a single, GPU-visible descriptor heap (and a separate sampler heap) for the entire frame or application lifetime. Partition the global heap into functional regions to prevent fragmentation and simplify lifecycle management. A static / persistent region (Lower Range). This holds long-lived global resources (bindless textures, material buffers, global buffers) that rarely change. Additionally, a dynamic / ring-buffer region (Upper Range). This acts as a lock-free ring buffer or free-list allocator for per-frame data, temporary staging, or frequent updates. For descriptor replication / copying: Copy descriptors into the shader-visible heap during resource creation/streaming.

As root signature strategy for a bindless architecture, use a minimal, global root signature shared across the vast majority of the Pipeline State Objects (PSOs) to eliminate driver overhead during PSO transitions. Use global root flags rather than descriptor tables, allowing shaders to index ResourceDescriptorHeap and SamplerDescriptorHeap directly via integer handles. Push / Root Constants for Index Passing: Pass resource indices, material IDs, and per-draw data via Root Constants (32-bit inlined values) rather than constant buffer views, as root constants incur zero heap indirection and offer the fastest access. Root Descriptors for Frequently Changing CBVs: Use Root Descriptors (direct GPU virtual addresses) inline in the root signature for per-draw or per-pass constant buffers instead of allocating heap slots.

For execution and shader unpacking, pass handles via constants: Send packed resource indices or 64-bit GPU buffer pointers through root/push constants or a root-bound constants buffer. Or use direct indexing in HLSL: Unpack the index inside the shader and index into ResourceDescriptorHeap[index] or alias it into typed resource objects.

The second component is a high-level rendering api that exposes a render graph. The render graph allows for grouping of render, compute and/or copy commands into logical groups, so called render passes. The render graph is to be rebuild every frame. The render graph should be build and executed in a three step process. The first step is the building of the render passes. Besides graphics passes, the render graph should have first-class support for compute and copy passes. In this step the render graph should track which resources are created within a render pass, which inputs are used from earlier defined render passes and which outputs can be used in later render passes. This build phase should be used as the basis for the graph like data structure. The inputs and/or outputs of the render passes should be virtualized resources. Additionally, the render graph should be capable handling external resources. These should be imported into the render graph structure. The second phase in the execution is the compilation phase. In this phase the graph like data structure is used to cull unnecessary render passes from the execution because its virtual resources are never referenced. Also, this phase determines the execution order of the render passes, the lifetime of the virtualized resources and necessary state transitions of the resources to fulfill the requirements of the underlying graphics API. To reduce the amount of GPU memory used during execution, resource aliasing and transient memory pooling should be able to be handled. The third phase will be the execution phase of the render graph. In this phase, the virtual resources will be linked to concrete GPU resources that can be used during the execution of actual render commands and the different render passes will be executed. Note that the render graph should be able to handle multi-view support.

The Avis library should also have a scene management component. The component should hold and track all distinct entities that can be found within a scene. The management should be based on entity component systems. For this, the external entt-4.0.0 library is available in the folder `external/entt-4.0.0/`. The components that should be provided are mesh, material, vehicle and sensor. The mesh and texture formats should be based on glTF. For materials, use the PBR metallic-roughness model. In addition, a separate scene graph structure should be used for orchestrating the positional relations between entities. This scene graph should also handle world transform propagtion. Synchronization of the scene from the simulation thread to the renderer should be done based on a snapshot with double buffering semantics.

The Avis library should also have a io layer that is capable of asynchronous loading and writing of files. For implementation of the asynchronous machinery, use the sender-receiver pattern. This is provided by the stdexec library in the folder `external/stdexec/`. As underlying library, use ASIO to implement the async file operations. The execution context should run on a thread within the threadpool implementation that is available within the Avis library. Errors should be propagated through the use of set_error.

The Avis library should have a custom threadpool implementation. The threadpool should be available within the Avis library as a component that is initialized and generally available when the Avis library is initialized. The number of threads within the threadpool should be configurable. When the usage of the Avis library is finished, the threadpool should also release all its threads by signalling to each thread to finish execution. After the finish signal, it should wait until all threads are actually finished.
